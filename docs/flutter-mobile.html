Flutter Mobile App — Architecture & Specification

Target document. This is the complete, implementation-ready specification for the companion Flutter mobile client that shares this Laravel backend. An IDE agent should be able to scaffold the entire app from this document without re-deriving any decision.

Companion documents: API.md (the wire contract), SOFTWARE_ARCHITECTURE.md (the backend).

1. Scope & role policy

The mobile app is a field client for the operational side of the platform. It is deliberately not a full replacement for the web console.

RoleMobile accessRationale
Member✅ FullThe primary mobile user. Personal balance, meal history, deposits, payments, voting, claims.
Meal Manager✅ FullRecords meals/deposits/expenses in the field — the highest-value mobile use case.
Institution Admin✅ FullApproves, monitors and configures their own workspace on the move.
Software Super Admin❌ BLOCKED — web onlyGlobal, cross-tenant platform operations (institution registry, SaaS billing, FX, cross-tenant audit) are inherently desktop, high-risk, and have no tenant scope in the API. See §9.

1.1 The SSA exclusion is enforced in three layers

The SSA must never reach a mobile session. Defence in depth:

  1. API guard (authoritative). POST /api/auth/login refuses to issue a token to

an SSA account, returning 403 with { "message": "Platform administrators must use the web console." }.

  1. Token guard. GET /api/auth/me returns the same 403 if a stored token

resolves to an SSA, so a token minted before this rule cannot be reused.

  1. Client guard. The login screen surfaces the 403 message verbatim and never

persists the token. See AuthRepository.login.

Implemented (v1). Layers 1 and 2 are live in App\Http\Controllers\Api\AuthController::login() and ::me(), sharing a single SSA_MOBILE_REFUSAL constant so the refusal reads identically in both places. The old documented behaviour — an SSA token resolving to a global, unscoped context (API.md §5) — is no longer reachable through the API, closing that data-exposure path.

3.2 Why BLoC here

A finance client has a small number of long-lived, stateful screens (the day's meal grid, the member roster, the balance summary) where the sequence of transitions matters. BLoC makes those transitions explicit and replayable:

MealsDayLoadRequested
  → MealsDayLoading           (show skeleton)
  → MealsDayLoaded            (cached data, marked stale)
  → MealsDaySynced            (server truth replaced cache)
  → MealsDaySaveRequested
  → MealsDaySaving            (rows locked, spinner on the button)
  → MealsDaySaveSuccess       (optimistic rows confirmed)
     └─ on failure → MealsDaySaveQueued (offline: queued, not lost)

A ChangeNotifier would collapse these into one mutable object and lose the "queued vs saved" distinction — which is the single most important state in an offline-first app.

Conventions

  • One BLoC per screen. BlocProvider at the route, BlocBuilder for UI,

BlocListener for navigation/snackbars — never for rendering.

  • Events are past-tense facts (MealsDaySaved), states are adjectives

(MealsDayLoaded). Use freezed unions so switch is exhaustive.

  • Repositories never throw into the presentation layer; they return

Either<Failure, T> (dartz or a hand-rolled Result<T>).

4. Networking — Dio

4.1 Client construction

// core/network/dio_client.dart
@singleton
class DioClient {
  DioClient(this._tokenStore, this._connectivity) {
    _dio = Dio(BaseOptions(
      baseUrl: Env.apiBaseUrl,                 // e.g. https://host/api
      connectTimeout: const Duration(seconds: 15),
      receiveTimeout: const Duration(seconds: 20),
      sendTimeout:    const Duration(seconds: 20),
      headers: {
        'Accept': 'application/json',
        'Content-Type': 'application/json',
      },
    ))
      ..interceptors.addAll([
        AuthInterceptor(_tokenStore, _onUnauthorised),
        InstitutionInterceptor(),
        ConnectivityInterceptor(_connectivity),
        ErrorInterceptor(),                       // LAST: maps to Failure
      ]);
  }

  late final Dio _dio;
  Dio get dio => _dio;
}

Interceptor order is load-bearing. Auth must run before anything that could short-circuit, and the error mapper must be last so it sees the final response.

4.2 AuthInterceptor — token handling

class AuthInterceptor extends Interceptor {
  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) async {
    final token = await _store.readToken();
    if (token != null && !options.path.startsWith('/auth/login')) {
      options.headers['Authorization'] = 'Bearer $token';
    }
    handler.next(options);
  }

  @override
  void onError(DioException err, ErrorInterceptorHandler handler) async {
    // 401 => the token is gone or expired. Do NOT retry in a loop.
    if (err.response?.statusCode == 401) {
      await _store.clear();
      _onUnauthorised();          // router redirects to /login
    }
    handler.next(err);
  }
}

Token lifetime is 30 days (API.md §4). Treat 401 as terminal: clear the token, return to login, never retry the same token.

403 is not 401. A 403 means authenticated but refused — an inactive account, or (for this app) an SSA. Surface the server's message; do not sign the user out.

4.3 InstitutionInterceptor — multi-institution headers

A user belongs to exactly one institution, so the tenant is implied by the token and the app must not attempt to choose one. The interceptor's job is to make that explicit and to carry the active workspace's identity for diagnostics.

class InstitutionInterceptor extends Interceptor {
  @override
  void onRequest(RequestOptions options, RequestInterceptorHandler handler) {
    final session = sl<SessionStore>();

    // X-Institution-Id is a DIAGNOSTIC + guard header, not a tenant selector.
    // The server derives the real tenant from the token and ignores any attempt
    // to point elsewhere; a mismatch is logged as a client bug.
    if (session.institutionId != null) {
      options.headers['X-Institution-Id'] = '${session.institutionId}';
      options.headers['X-Client-Platform'] = 'mobile';
      options.headers['X-Client-Version']  = Env.appVersion;
    }
    handler.next(options);
  }
}

Never send a tenant the token does not own. The API's BelongsToInstitution global scope and tenantExists() validation already reject cross-tenant ids with 404/422 (API.md §5); the header exists so a bug is visible rather than silently mis-scoped.

5. Offline-first

5.1 What is cached, and for how long

The rule: cache what the user is standing in front of; never cache history.

DataCached?TTLNotes
/api/meta✅24 hTerminology, currency, subsidy modes. Re-fetched on tenant change.
/api/auth/me✅sessionRevalidated on every cold start.
/api/dashboard (current month)✅15 minThe home screen.
/api/members (roster)✅30 minNeeded to record meals offline.
/api/meals/day (today ± 2 days)✅24 hThe critical offline case — the day grid.
/api/deposits (current month)✅15 min
/api/subsidies/sources✅7 dConfiguration; rarely changes.
Historical months (> 1 month old)❌ NEVER—Explicitly excluded. Stale financial history is worse than no history: a user could act on a superseded balance. The UI requires connectivity for past months.
Reports / analytics / forecast❌—Server-computed aggregates; must be fresh.
Meal menu votes (tallies)❌—Counts change constantly; stale tallies mislead voters.

Why excluding history is the right default. The app's value is the current balance and today's meal sheet. A two-month-old deposit list cached on the device is (a) large, (b) almost never read offline, and (c) the most likely thing to be stale in a way that causes a wrong decision. Fetching it on demand keeps the offline dataset small enough to keep correct.

5.2 Isar collections

@collection
class CachedMealDay {
  Id id = Isar.autoIncrement;
  @Index(unique: true, replace: true)
  late String cacheKey;      // "<institutionId>:<yyyy-MM-dd>"
  late DateTime date;
  late String payloadJson;   // the raw API object, verbatim
  late DateTime cachedAt;
}

@collection
class CachedMember {
  Id id = Isar.autoIncrement;
  @Index(unique: true, replace: true)
  late String cacheKey;      // "<institutionId>:<memberId>"
  late int memberId;
  late String payloadJson;
  late DateTime cachedAt;
}

@collection
class PendingMutation {
  Id id = Isar.autoIncrement;
  late String endpoint;      // POST target
  late String method;
  late String bodyJson;
  late String idempotencyKey;   // client-generated UUID
  late DateTime queuedAt;
  late int attemptCount;
  String? lastError;
}

payloadJson stores the raw response envelope, not a re-serialised model. This is deliberate: a new server field flows through to the UI after an app update without a cache-schema migration.

5.3 The sync engine

connectivity_plus stream ──┐
app lifecycle (resumed)  ──┼──> SyncScheduler ──> SyncService.run()
manual pull-to-refresh   ──┘

SyncService.run() is serialised (a single-flight mutex) and ordered:

  1. Flush the outbox first. Pending mutations are the user's intent and must

reach the server before any read, or a pull could overwrite optimistic state.

  1. Re-read the invalidated caches. Only the keys the flushed mutations touch,

plus the home screen.

  1. Reconcile. Server truth replaces the cache. Any optimistic row whose server

counterpart is missing is surfaced — never silently dropped.

Idempotency. Every queued write carries a client-generated idempotencyKey. The server should treat a repeat of the same key as a no-op and return the original result, so a retry after a dropped response cannot double-post a deposit.

Conflict policy — last-write-wins per record, with a visible report. Meal-entry and deposit writes are per-member-per-day (or append-only), so genuine concurrent edits are rare. When the server rejects a queued write:

Server responseAction
422 validationMark the queue item failed, keep it, show it in a "needs attention" list. Never discard user input.
404 (record deleted)Drop the item, tell the user which one and why.
409 conflictKeep the item, surface both versions, let the user choose.
5xx / networkRetry with exponential backoff (1s, 2s, 4s, 8s, 30s, capped).

Backoff + cap. After 6 attempts an item parks as failed and is surfaced in the UI. An unbounded retry loop drains the battery and hides a real problem.

5.4 Offline UX contract

  • A persistent banner appears the moment connectivity drops, stating what still

works: "Offline — you can still record meals and deposits. Changes sync automatically."

  • Every screen that reads uncached data shows a stale-data chip with the

cache timestamp, not a spinner forever.

  • Every queued write shows a pending badge on the row it affects. The user must

never wonder whether their entry was saved.

  • Writes that cannot be queued (reports, votes) are disabled with a reason, not

silently failed.

6.3 Handling

  • Foreground: show an in-app banner (the OS suppresses the tray notification);

refresh the affected screen.

  • Background tap: route via the data.deep_link field, resolving through

go_router's deep-link handler.

  • Cold start from a notification: buffer the payload in bootstrap.dart and

replay it once the router and session are ready. This is the classic bug — the tap that launches the app must not be swallowed.

  • Permission: request after the first successful login with a soft prompt

("Get notified when your deposit is verified"), never on first launch.

  • Tenant safety: a notification for another institution must be dropped if the

session's institution_id does not match.

7.4 Branding hierarchy — the same rule as the web

The mobile drawer header must apply the identical tenant-vs-platform logic as resources/js/Components/Sidebar.jsx:

  • A tenant user (Member / Meal Manager / Institution Admin): the institution's

name, subtitle and logo — falling back to the software logo when the institution has not uploaded one.

  • An SSA: never reaches the app (§1). The rule is stated here only so the

component is written correctly from the start.

Widget buildBrandHeader(BuildContext ctx) {
  final meta = ctx.watch<MetaCubit>().state.meta;
  final platform = ctx.watch<MetaCubit>().state.platform;

  // Tenant context: the institution's identity, software logo as fallback.
  final name = meta?.institution?.name ?? platform.controlCenter;
  final subtitle = meta?.institution?.subtitle
      ?? meta?.institution?.typeLabel
      ?? 'Shared meals, tracked';
  final logoUrl = meta?.institution?.logoUrl;      // null => software logo

  return DrawerHeader(
    child: Row(children: [
      logoUrl != null
          ? Image.network(logoUrl, height: 32, width: 32)
          : const SoftwareLogoMark(),               // the shared fallback
      const SizedBox(width: 12),
      Expanded(child: Column(
        crossAxisAlignment: CrossAxisAlignment.start,
        mainAxisAlignment: MainAxisAlignment.center,
        children: [
          Text(name,     style: AppTypography.brandTitle, overflow: TextOverflow.ellipsis),
          Text(subtitle, style: AppTypography.brandSubtitle, overflow: TextOverflow.ellipsis),
        ],
      )),
    ]),
  );
}

7.5 Terminology — never hard-code a noun

The institution's type decides whether members are Students, Employees, Boarders or Members. /api/meta returns a terms map; all copy reads it:

// ✅ correct
Text(ctx.t('members'))            // "Students" | "Employees" | "Boarders" | "Members"

// ❌ never
Text('Students')

Money is formatted only from /api/meta's currency block — symbol, position, separators, precision, abbreviation threshold. A hard-coded ৳ is a bug.
